# ANTIGRAVITY.md — Contrat d'interface du projet externe

> **Instructions** : Copiez ce fichier dans le répertoire racine de votre projet externe
> sous le nom `ANTIGRAVITY.md`. Il sert de contrat d'interface entre votre projet et
> l'agent Antigravity, qui s'en sert pour comprendre votre service et générer
> automatiquement les ressources nécessaires (tests, interface, intégration plateforme).

---

## Identité du projet

| Champ | Valeur (à remplir) |
|---|---|
| **name** | `mon-service` *(kebab-case, ex: ia-dev-memory)* |
| **lb_path** | `/mon-service` *(chemin LB, doit commencer par `/`)* |
| **version** | `v0.1.0` *(semver: vX.Y.Z)* |
| **description** | Courte description fonctionnelle du service |
| **owner** | Email du développeur responsable |

---

## Structure requise

Votre projet **doit** contenir les éléments suivants à sa racine pour être accepté
par `manage_env.py` lors du déploiement :

```
<votre-projet>/
├── Dockerfile          ← Image Docker du service (multi-stage, non-root)
├── database/           ← Migrations Liquibase
│   └── changelogs/
│       └── db.changelog-master.yaml
├── terraform/          ← Modules Terraform Cloud Run
│   ├── main.tf
│   ├── variables.tf    ← Doit déclarer les 10 variables ci-dessous
│   └── outputs.tf
└── ANTIGRAVITY.md      ← Ce fichier
```

## Interface Terraform — Variables injectées automatiquement

`manage_env.py` injecte **10 variables** dans votre `terraform/variables.tf` lors du déploiement.
**Toutes doivent être déclarées** — même si vous n'utilisez pas certaines d'entre elles.

### Variables d'identité (depuis le YAML d'environnement)

| Variable | Source | Exemple |
|---|---|---|
| `project_id` | `envs/<env>.yaml` → `project_id` | `prod-ia-staffing` |
| `region` | `envs/<env>.yaml` → `region` | `europe-west1` |

### Variables du projet externe (depuis `extra_projects[]` dans le YAML)

| Variable | Source | Exemple |
|---|---|---|
| `service_name` | `extra_projects[].name` | `ia-dev-memory` |
| `image_version` | `extra_projects[].version` | `v0.1.0` |
| `image`         | Construit par manage_env.py : `{registry}/{name}:{version}` | `europe-west1-docker.pkg.dev/.../ia-dev-memory:v0.1.0` |
| `lb_path` | `extra_projects[].lb_path` | `/ia-dev-memory` |

### Variables réseau (depuis les outputs Terraform de la plateforme)

| Variable | Source | Exemple de valeur |
|---|---|---|
| `vpc_network_id` | `terraform output vpc_network_id` (plateforme) | `projects/proj/global/networks/vpc-dev` |
| `vpc_subnet_id` | `terraform output vpc_subnet_id` (plateforme) | `projects/proj/regions/europe-west1/subnetworks/subnet-dev` |
| `alloydb_instance_uri` | `terraform output alloydb_instance_uri` (plateforme) | `projects/proj/locations/europe-west1/clusters/alloydb-dev/instances/primary-dev` |
| `alloydb_ip` | `terraform output alloydb_ip` (plateforme) | `10.0.0.5` |

### Variables base de données (plateforme + YAML)

| Variable | Source | Exemple |
|---|---|---|
| `alloydb_database` | `extra_projects[].alloydb_database` (défaut: `name` avec tirets→underscores) | `ia_dev_memory` |
| `service_account_email` | `terraform output extra_project_sa_emails[name]` (plateforme) | `sa-ia-dev-memory-dev@proj.iam.gserviceaccount.com` |

> **La plateforme crée automatiquement** un Service Account, les rôles IAM AlloyDB (`alloydb.client` + `alloydb.databaseUser`) et un utilisateur IAM AlloyDB lié au SA. Le projet externe n'a qu'à utiliser le SA via `var.service_account_email`.

### Backend GCS (auto-généré par manage_env.py)

manage_env.py **génère automatiquement** un fichier `terraform/backend.tf` dans votre projet :

```hcl
# AUTO-GENERATED by manage_env.py — ne pas modifier manuellement.
terraform {
  backend "gcs" {
    bucket = "z-gcp-summit-tf-state"         # bucket de la plateforme
    prefix = "terraform/state/{env}/{name}"  # isolé par env et projet
  }
}
```

> ⚠️ **Ne créez pas de `backend.tf` manuellement** — il sera écrasé à chaque déploiement.
> ⚠️ **N'ajoutez pas de bloc `terraform { backend ... }` dans votre `main.tf`** non plus.

### Variables IAP OAuth (depuis Secret Manager)

Ces variables contiennent le **nom** du secret GCP Secret Manager, pas la valeur.
Votre Terraform les utilise avec `google_secret_manager_secret_version_access`.

| Variable | Valeur injectée | Secret Manager attendu |
|---|---|---|
| `iap_oauth_client_id` | `iap-oauth-client-id-{env}` | Secret créé lors du bootstrap IAP |
| `iap_oauth_client_secret` | `iap-oauth-client-secret-{env}` | Secret créé lors du bootstrap IAP |

> **Note IAP** : Les secrets IAP OAuth sont créés **en dehors** de Terraform lors de la
> configuration initiale d'IAP (Google Cloud Console → API & Services → Credentials).
> La convention de nommage `iap-oauth-client-id-{env}` est imposée par la plateforme.

## Exemple d'utilisation dans `terraform/main.tf`

```hcl
# Lecture des secrets IAP depuis Secret Manager
data "google_secret_manager_secret_version" "iap_client_id" {
  secret  = var.iap_oauth_client_id
  project = var.project_id
}

data "google_secret_manager_secret_version" "iap_client_secret" {
  secret  = var.iap_oauth_client_secret
  project = var.project_id
}

# Cloud Run avec Direct VPC Egress pour accès réseau interne
resource "google_cloud_run_v2_service" "main" {
  name     = "${var.service_name}-${var.region}"
  location = var.region
  project  = var.project_id

  template {
    containers {
      image = var.image
      env {
        name  = "ENV"
        value = terraform.workspace
      }
      env {
        name  = "VERSION"
        value = var.image_version
      }
    }

    # Accès au VPC interne de la plateforme (AlloyDB, Redis, LB interne)
    vpc_access {
      network_interfaces {
        network    = var.vpc_network_id
        subnetwork = var.vpc_subnet_id
      }
      egress = "PRIVATE_RANGES_ONLY"
    }
  }
}

# Backend Service pour le Load Balancer
resource "google_compute_backend_service" "main" {
  name    = "backend-${var.service_name}-${terraform.workspace}"
  project = var.project_id

  # IAP activé sur le backend
  iap {
    oauth2_client_id     = data.google_secret_manager_secret_version.iap_client_id.secret_data
    oauth2_client_secret = data.google_secret_manager_secret_version.iap_client_secret.secret_data
  }
}
```

## Endpoints exposés

Remplissez ce tableau pour décrire l'API de votre service.
Antigravity s'en servira pour générer les tests de santé et l'intégration frontend.

| Méthode | Chemin | Description | Auth JWT |
|---|---|---|---|
| GET | `/health` | Health check (doit retourner `{"status": "ok"}`) | ❌ Non |
| GET | `/api/...` | *(à compléter)* | ✅ Oui |
| POST | `/api/...` | *(à compléter)* | ✅ Oui |

> **Endpoint de sanity check** : `GET /health` (port `8080`) — utilisé par le Load Balancer GCP
> pour déterminer si l'instance est saine.

## Contrat Dockerfile

Votre `Dockerfile` doit respecter les contraintes de la plateforme Zenika :

```dockerfile
# ✅ Multi-stage build (réduire la taille de l'image)
FROM python:3.12-slim AS builder
# ... étape de build ...

FROM python:3.12-slim
# ✅ Utilisateur non-root obligatoire
RUN adduser --disabled-password --gecos "" appuser
USER appuser

# ✅ CMD sans shell (pas de sh -c)
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]
```

## Migrations Liquibase

Structure minimale du répertoire `database/` :

```yaml
# database/changelogs/db.changelog-master.yaml
databaseChangeLog:
  - changeSet:
      id: 001-init
      author: votre-nom
      changes:
        - createTable:
            tableName: example
            columns:
              - column:
                  name: id
                  type: UUID
                  constraints:
                    primaryKey: true
      rollback:
        - dropTable:
            tableName: example
```

> **Règle** : Chaque `changeSet` doit avoir une section `rollback` (Golden Rules §Checklist).
